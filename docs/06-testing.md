# Тестирование

## Что реально запускается и проходит

По состоянию на дату написания:

```
Unit-тесты (vitest run):        5 passed  (1 файл)
E2E-тесты (npm run test:e2e):  13 passed  (4 файла)
Frontend build (ng build):     без ошибок TypeScript/шаблонов
Backend typecheck (tsc):       без ошибок
```

Оба набора можно запустить сейчас же: `cd backend && npm test` и `cd backend && npm run test:e2e`.

## Инфраструктура тестирования

E2E-тесты поднимают реальное NestJS-приложение (`Test.createTestingModule` + `app.init()`) и стучатся в него через `supertest`, то есть проходят через настоящие guard’ы, ValidationPipe и Prisma — не моки. Чтобы не портить демонстрационные данные в рабочей базе (`fsin_crm`), тесты работают с **отдельной базой** `fsin_crm_test`:

- `backend/test/setup-env.ts` подменяет `DATABASE_URL` до того, как что-либо импортирует `PrismaService`
- `npm run test:e2e` сначала выполняет `pretest:e2e` (`prisma migrate reset` + `seed`, оба — с `DATABASE_URL` из `.env.test`), то есть каждый запуск стартует с чистого, воспроизводимого состояния

Unit-тест использует мок `PrismaService` (обычный объект с `vi.fn()`) — никакой БД не требует вообще.

## Что покрыто и как

### `attendance.service.spec.ts` (unit, 5 тестов)
Бизнес-правила `AttendanceService.updateRecord` в изоляции:
- отклоняет отметку отсутствия без причины
- принимает отметку отсутствия с причиной
- отклоняет правку закрытого табеля
- отклоняет правку табеля вне scope пользователя
- отдаёт `NotFoundException` на несуществующий табель

### `course-transition.e2e-spec.ts` (3 теста)
- `preview` возвращает переходы и корректную сводку (`toPromote + toGraduate + toSkip === total`)
- **повторный запуск `execute` не переводит студентов ещё раз** — первый запуск сохраняет курс студента, второй запуск даёт `promoted: 0`, курс не меняется. Этот тест не формальность: он поймал реальный баг (см. ниже)
- старшина получает `403` при попытке вызвать предпросмотр перевода курса

### `attendance-lifecycle.e2e-spec.ts` (4 теста)
- создание табеля помечает всех активных студентов группы присутствующими по умолчанию, `validation.isComplete === true` сразу после создания
- отметка отсутствия без причины отклоняется (`400`) на уровне API, не только в форме
- табель с корректно заполненными причинами успешно проходит `submit`
- старшина не может создать табель для группы вне своего scope (`403`)

### `rbac-scope.e2e-spec.ts` (5 тестов)
- админ видит все группы, старшина — только назначенную
- два старшины видят непересекающиеся наборы групп
- запрос без токена — `401`
- менеджер получает `403` на admin-only маршруте (`/audit`)
- список студентов у старшины содержит только студентов его группы

### `imports-validation.e2e-spec.ts` (1 тест, самый показательный)
Собирает `.xlsx` из 12 строк (10 валидных + 2 с несуществующей группой) через `ExcelJS` прямо в тесте, прогоняет через реальный HTTP-пайплайн `parse → mapping → validate → confirm` и проверяет:
- `parse` возвращает `totalRows: 12`, но `previewData.length === 10` (превью — это ограничение отображения, не данных)
- `validate` находит **все 12** строк, а не только 10 из превью: `validRows: 10, errorRows: 2`
- после `confirm` число реально созданных студентов в БД (разница `GET /students` до/после) равно именно 10, не 12 и не 10-из-урезанного-набора

## Реальные баги, найденные в процессе разработки и тестирования

Ниже — то, что было действительно сломано, а не гипотетические риски. Каждый пункт исправлен и проверен (тестом или вручную через curl/Playwright).

| # | Баг | Как нашли | Исправление |
|---|---|---|---|
| 1 | `imports.confirm()` помечал импорт «завершён», не создавая ни одного студента в БД | Ручная проверка через curl | Переписан на реальное создание `Student` в транзакции из сохранённых валидных строк |
| 2 | `imports.validate()` принимал строки от клиента; клиент физически не мог передать больше 10 (превью), значит файлы с >10 строками валидировались бы неверно | Анализ контракта parse→validate при написании фронтенд-мастера | Полный набор строк сохраняется на сервере (`ImportJob.rawData`), `validate` больше не принимает `rows` от клиента |
| 3 | `POST /students` и `POST /users` брали `organizationId` из тела запроса, а не из JWT | Ревью кода при подключении фронтенда | Оба эндпоинта теперь всегда используют `organizationId` авторизованного пользователя |
| 4 | Автоматический перевод курса не был идемпотентным: повторный `execute()` в тот же день/цикл продвигал курс ещё раз, потому что проверка сравнивала текущее состояние с заново пересчитанным `toCourse`, который после первого перевода уже не совпадал | Написание e2e-теста на идемпотентность (пункт 2 списка выше) | Проверка переписана на факт наличия автоматической записи в `StudentCourseHistory` с начала текущего учебного года |
| 5 | `AppController`/`AppService` (стартовый Nest-боилерплейт) не были подключены в `AppModule` — их маршрут никогда не работал, включая штатный тест из шаблона проекта | Тест `app.e2e-spec.ts` падал с `404` | Мёртвый код и бессмысленный тест удалены |
| 6 | `GET /audit?limit=5` падал с `500` — `page`/`limit` из query-строки не приводились к числу перед передачей в Prisma | Ручная проверка через curl | Явное `Number()` |
| 7 | `students.component.html` показывал «—» вместо названия группы — фронтенд обращался к несуществующему полю `group` вместо `currentGroup` | Playwright-скриншот админ-списка студентов | Поле модели исправлено |
| 8 | Prisma был закреплён на experimental-версии `8.0.0-rc.15` с полностью другим CLI (`prisma db`/`prisma contract` вместо `prisma migrate`) — ни `generate`, ни `migrate dev` не работали вообще | Первая попытка запустить `npm run db:migrate` | Понижено до стабильной `5.22.0` |

## Что не тестировалось автоматически

- Frontend-компоненты не имеют собственных unit/component-тестов (Angular TestBed) — проверка UI шла через Playwright как end-to-end сценарии поверх реального backend, что и зафиксировано скриншотами в ходе разработки, но не оформлено в постоянный набор тестов в репозитории
- Нагрузочное и security-тестирование не проводилось — это дипломный прототип, не система, готовая к промышленной эксплуатации (см. `09-vkr-materials.md`, раздел об ограничениях)

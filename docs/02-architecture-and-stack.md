# Архитектура и выбор технологий

## Архитектурный стиль: модульный монолит

Backend — один процесс NestJS с 19 независимыми feature-модулями (`students`, `groups`, `attendance`, `imports`, `reports`, `audit`, …), каждый со своим контроллером, сервисом и (где нужно) DTO. Frontend — одно Angular-приложение с lazy-loaded standalone-компонентами по функциональным областям.

**Почему не микросервисы.** Система имеет одну зону ответственности (учёт контингента и посещаемости одной организации), несколько разработчиков её не пишут параллельно, и нагрузка не требует независимого масштабирования отдельных частей. Микросервисы решают проблемы координации больших команд и независимого деплоя частей системы — здесь этих проблем нет, а их цена (сетевые вызовы вместо вызовов функций, распределённые транзакции, отдельная инфраструктура на каждый сервис) была бы чистым злом для дипломного прототипа с одним backend-процессом. Модульный монолит даёт то же разделение ответственности на уровне кода (изолированные NestJS-модули с явными границами через `imports`/`exports`), но без операционной сложности распределённой системы.

**Почему не «один большой файл».** Внутри монолита модули всё равно изолированы: `StudentsModule` не знает о внутренностях `AttendanceModule`, они взаимодействуют только через `PrismaService` (общий, `@Global()`) и HTTP-слой контроллеров. Это даёт основной плюс микросервисной модульности (можно рассуждать о модуле отдельно, можно вынести в отдельный сервис позже, если понадобится) без её цены.

## Технологический стек

| Слой | Технология | Почему именно она |
|---|---|---|
| Frontend framework | Angular 19 (standalone components) | Строгая типизация, встроенный DI, Router и HttpClient «из коробки» — не нужно самостоятельно собирать инфраструктуру из библиотек, как в случае с более лёгкими фреймворками. Standalone API убирает лишний NgModule-боилерплейт |
| Frontend state | Angular Signals | Задача не требует Redux/NgRx — состояние страниц локальное и простое (списки, формы, фильтры). Signals дают реактивность без дополнительной библиотеки и её концептуальной цены |
| Backend framework | NestJS 12 | Модульность «из коробки» (то, что нужно для монолита с чёткими границами), decorator-based DI, встроенные Guards/Pipes для RBAC и валидации — то есть именно то, что нужно для системы с ролевым доступом и строгой валидацией входных данных |
| ORM | Prisma 5 | Типобезопасные запросы, генерируемые прямо из схемы — ошибка в имени поля обнаруживается на этапе компиляции, а не в проде. Декларативные миграции (`prisma migrate dev`) снимают необходимость писать SQL-миграции вручную |
| БД | PostgreSQL 16 | Реляционная модель подходит предметной области (студенты, группы, табели, история — всё это сущности со связями и целостностью, которую easier поддерживать через внешние ключи, чем в документо-ориентированной БД). Open-source, бесплатно, стандарт де-факто для реляционных данных в этом масштабе |
| Аутентификация | JWT (`@nestjs/jwt`, `passport-jwt`) | Stateless-токен подходит для SPA-клиента без сессионного состояния на сервере; access-token короткоживущий (15 минут), обновление — через `refresh`-эндпоинт |
| Хеширование паролей | Argon2 | Текущий рекомендуемый алгоритм (в отличие от bcrypt — устойчивее к атакам на GPU), встроенная поддержка через `argon2` |
| Excel | ExcelJS | Единственная зрелая chistая JS/TS-библиотека для чтения и генерации `.xlsx` без внешних зависимостей на системном уровне |

## Почему frontend и backend — раздельные приложения

Это не техническое ограничение, а осознанное разделение ответственности: frontend не может импортировать backend-код физически (они в разных `node_modules`, разных `tsconfig`), значит бизнес-логика гарантированно не «утечёт» в браузер, а backend не может случайно получить прямую зависимость от Angular. Связь — только через REST API по HTTP. Это также прямое требование задания и стандартная практика: клиент и сервер имеют разные жизненные циклы деплоя (можно обновить один без другого).

## Почему без Docker в этой версии

Контейнеризация — операционная надстройка над уже работающей системой, а не часть бизнес-логики. Ставить Docker поверх и без того нетривиальной первой версии (Node.js + PostgreSQL + два процесса) усложнило бы именно то, что должно быть простым и понятным для локального запуска и защиты — команды `npm install` → `npm run start:dev`/`npm start` проще объяснить и продемонстрировать, чем `docker compose up` с разбором Dockerfile на защите. Docker — разумное следующее направление развития (см. `08-run-guide.md`), но не требование для рабочего прототипа.

## Взаимодействие компонентов на примере одного запроса

`GET /api/groups` (старшина открывает «Табель»):

1. Angular `GroupsService.list()` → `HttpClient.get('/api/groups')`
2. `authInterceptor` добавляет заголовок `Authorization: Bearer <token>`
3. NestJS: `JwtAuthGuard` проверяет и декодирует токен → `RolesGuard` (если на маршруте есть `@Roles`) → `GroupsController.findAll`
4. `GroupsService.findAll` смотрит `userContext.roles`: если это `foreman`, подставляет `WHERE id IN (userContext.groupScopeIds)` в Prisma-запрос
5. Prisma генерирует SQL, PostgreSQL возвращает строки
6. Ответ сериализуется в JSON, уходит обратно в Angular, попадает в сигнал компонента, шаблон перерисовывается

Ни на одном из шагов frontend не знает, что бизнес-правило «старшина видит только свою группу» вообще существует — оно целиком на backend, что исключает возможность обойти его, изменив клиентский код.

## Альтернативы, которые рассматривались и почему отклонены

- **Микросервисы** — избыточная сложность для одной зоны ответственности (см. выше)
- **MongoDB вместо PostgreSQL** — данные предметной области реляционные по своей природе (студент принадлежит группе, группа — направлению, табель ссылается на период и группу); document-store не даёт ничего взамен потерянной ссылочной целостности
- **REST vs GraphQL** — REST достаточен для конечного набора экранов административной системы; GraphQL решает проблему over-/under-fetching на масштабе, которого здесь нет
- **NgRx вместо Signals** — оверинжиниринг для состояния уровня «список + форма фильтра» на каждой странице

# Функциональная логика по модулям

Для каждого модуля: назначение, пользовательские действия, бизнес-правила, где реализовано.

## Авторизация (`auth`)

**Назначение:** вход в систему, выпуск и обновление JWT, смена пароля.

- `POST /api/auth/login` — email + пароль → `accessToken` (15 минут), `refreshToken`, данные пользователя (роли, permissions)
- `POST /api/auth/refresh`, `POST /api/auth/logout`, `POST /api/auth/change-password`, `GET /api/auth/profile`

**Бизнес-правила:**
- Пароль хранится только как Argon2-хеш (`passwordHash`), в открытом виде нигде не сохраняется и не логируется
- Неактивный (`isActive: false`) или заблокированный (`isBlocked: true`) пользователь не может войти — `UnauthorizedException` до проверки пароля
- При блокировке пользователя (`UsersService.block`) все его активные refresh-токены отзываются (`revokedAt`), это немедленно инвалидирует уже открытые сессии на обновление токена

**Frontend:** `features/auth/login/`, `core/services/auth.service.ts` (хранит токен в `localStorage`, отдаёт сигналы `isAdmin`/`isManager`/`isForeman`), `core/interceptors/auth.interceptor.ts` (подставляет заголовок, разлогинивает при 401)

## Пользователи (`users`)

**Назначение:** админ создаёт и настраивает учётные записи сотрудников (не студентов).

**Пользовательские действия:** создать (email, пароль, ФИО, роли, group-scope, direction-scope), редактировать, заблокировать/разблокировать.

**Бизнес-правила:**
- `organizationId` при создании берётся из JWT текущего администратора, а не из тела запроса — клиент не может создать пользователя в чужой организации
- Роли, group-scope и direction-scope пересчитываются полностью при каждом обновлении (`deleteMany` + `createMany` в транзакции), а не патчатся точечно — проще гарантировать консистентность набора

**Frontend:** `features/admin/users/` — таблица + модальная форма с чекбоксами ролей/групп/направлений

## Роли и права (`roles`)

**Назначение:** просмотр матрицы permission × роль, включение/выключение конкретного права у конкретной роли.

**Бизнес-правила:** роли (`admin`, `manager`, `foreman`) — системные (`isSystem: true`), их нельзя удалить или переименовать через API; можно только менять состав permissions. На фронтенде дополнительно заблокировано редактирование прав роли `admin` — защита от случайной самоблокировки.

**Frontend:** `features/admin/roles/` — таблица, сгруппированная по модулю permission’а, с чекбоксами

## Студенты (`students`)

**Назначение:** карточка обучающегося и её история.

**Поля карточки:** ФИО, дата рождения, внутренний ID (уникален в пределах организации, необязателен), группа, курс, программа, статус, дата зачисления/завершения.

**Бизнес-правила:**
- Перевод в другую группу, смена статуса или курса всегда добавляет запись в соответствующую историю (`StudentGroupHistory`, `StudentStatusHistory`, `StudentCourseHistory`) — карточка хранит только *текущее* состояние, история — неизменяемый журнал
- Scope: руководитель видит только студентов своих направлений, старшина — только своей группы (фильтрация на уровне SQL-запроса, не на клиенте)

**Frontend:** `features/students/` — список с поиском + модальная форма создания/редактирования

## Группы (`groups`)

**Назначение:** учебные группы.

**Пользовательские действия (админ):** создать, редактировать, назначить/сменить старосту, архивировать.

**Бизнес-правила:**
- Назначение старосты (`GroupsService.assignForeman`) деактивирует предыдущего активного старосту группы и добавляет пользователю `UserGroupScope` на эту группу — то есть право доступа выдаётся автоматически вместе с назначением
- Архивирование — мягкое (`isArchived: true, isActive: false`), исторические данные группы не удаляются

**Frontend:** `features/groups/` — карточки групп + модалки создания и назначения старосты

## Табель посещаемости (`attendance`)

Центральный модуль системы, подробный процесс — в `04-business-processes.md`. Кратко по бизнес-правилам:

- При создании табеля (`createSheet`) все активные студенты группы получают записи со значением `isPresent: true` по умолчанию — так реализована формулировка ТЗ «отметить отсутствующих», а не «отметить присутствующих»
- Отметка отсутствия без `reasonId` отклоняется на уровне сервиса (`BadRequestException`), причём и в одиночном (`updateRecord`), и в массовом (`bulkUpdateRecords`) обновлении
- `submitSheet` проверяет: `present + absent === totalCount` (никто не пропущен) и что у всех отсутствующих указана причина; иначе — `BadRequestException` с точным числом непроверенных записей
- Статусная машина: `DRAFT → FILLED → SUBMITTED → REVIEWED → CLOSED`; закрытый табель (`CLOSED`) не редактируется никем, включая администратора, через штатные эндпоинты
- Настраиваемые поля табеля (`AttendanceField`) — отдельная модель с типами `BOOLEAN/TEXT/NUMBER/SELECT/MULTI_SELECT/DATE/TIME`, управляются из `admin/reference-data` (вкладка «Поля табеля»); значения по конкретной записи — `AttendanceFieldValue`

## Причины отсутствия (`attendance-reasons`)

Простой справочник (код, название, флаг «требует комментария»). Управляется из `admin/reference-data`.

## Автоматический перевод курса (`students/course-transition.service.ts`)

**Назначение:** ежегодный перевод студентов на следующий курс или завершение обучения — проектное решение, реализующее раздел 24 ТЗ (не подтверждено нормативным документом ФСИН, это архитектурное решение системы).

**Preview (только чтение):** для каждого активного студента со статусом «Обучается» и заполненными курсом и программой:
- если `currentCourse < program.maxCourse` → `PROMOTE` на `currentCourse + 1`
- если `currentCourse >= program.maxCourse` → `GRADUATE` (статус меняется на «Обучение завершено», `isActive: false`)
- если нет курса или программы → `SKIP`

**Execute:** применяет все переходы из preview в рамках одной транзакции на каждого студента, с идемпотентностью: студент, для которого уже есть автоматическая запись в `StudentCourseHistory` с начала текущего учебного года, повторно не переводится (без этой проверки повторный запуск за тот же цикл продвигал бы курс ещё раз — этот баг был найден и исправлен в ходе тестирования, см. `06-testing.md`). Каждое выполнение пишет запись в `AuditLog`.

**Frontend:** `features/admin/course-transition/` — сводка (сколько переходов какого типа), список всех переходов, кнопка выполнения с диалогом подтверждения

## Импорт Excel (`imports`)

**Назначение:** массовое создание студентов из `.xlsx`-файла.

**Процесс (4 шага, каждый — отдельный HTTP-запрос):**
1. `POST /imports/students/parse` — файл разбирается целиком (`ExcelJS`), полный набор строк сохраняется в `ImportJob.rawData`; клиенту возвращаются заголовки и превью первых 10 строк
2. `POST /imports/students/mapping` — сопоставление колонок файла с полями системы, сохраняется в `ImportJob.columnMapping`
3. `POST /imports/students/validate` — валидация **всех** сохранённых строк (не только превью): обязательность ФИО, существование группы/программы/статуса по коду; список ошибок с номером строки
4. `POST /imports/students/confirm` — реальное создание студентов из прошедших валидацию строк, в транзакции, с записью в `StudentGroupHistory` (если указана группа) и в `AuditLog`

**Бизнес-правило «нет скрытого частичного импорта»:** число импортированных строк, возвращаемое `confirm`, всегда равно числу строк, прошедших `validate` — это проверено e2e-тестом (см. `06-testing.md`), который специально гоняет файл из 12 строк, чтобы отличить «обработали все 12» от «обработали только первые 10 из превью».

**Frontend:** `features/admin/imports/` — пошаговый мастер (загрузка → сопоставление → проверка → итог)

## Экспорт (`exports`)

`GET /exports/students`, `GET /exports/attendance` — формируют `.xlsx` через `ExcelJS` и отдают файл как поток (`Content-Disposition: attachment`), без сохранения на диске сервера.

## Отчётность (`reports`)

- `GET /reports/dashboard` — данные для главной страницы, разные по ролям (см. `01-system-overview.md`)
- `GET /reports/summary` — таблица по всем активным группам организации (или отфильтрованным по направлению/курсу): число студентов, табелей, процент посещаемости
- `GET /reports/group/:id` — подробности по одной группе: список табелей за период + разбивка отсутствий по причинам
- `GET /reports/student/:id` — история посещаемости одного студента (реализовано на backend, frontend-страницы нет)

**Frontend:** `features/admin/reports/` — вкладки «Сводный отчёт» / «По группе»

## Аудит (`audit`)

`GET /audit` (только админ) — постраничный список действий с фильтрами по пользователю/сущности/действию/дате. Запись создаётся из сервисов при значимых мутациях (не автоматически для всех запросов — точечно, там где это явно вызвано, см. список мест в `05-database-and-api.md`).

## Организация (`organization`)

`GET/PATCH /organization` — реквизиты (название, краткое название, код). Одна запись на систему; таблица `Organization` заложена, чтобы систему можно было развернуть на другую организацию без переписывания кода, но в текущей версии она одна.

## Справочники (`directions`, `programs`, `academic-years`, `settings`)

Направления, образовательные программы (со сроком обучения и `maxCourse`, что напрямую используется автопереводом курса), учебные годы (с флагом «текущий», используемым идемпотентностью автоперевода), статусы студентов, периоды посещаемости («Утро»/«Вечер», расширяемо), поля табеля. Все управляются из единой страницы `features/admin/reference-data/` с вкладками.

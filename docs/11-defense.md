# Материалы к защите

Каждый ответ рассчитан на 20–60 секунд устной речи.

## Базовые вопросы (готовые ответы)

**Цель работы?**
Разработать информационную систему, автоматизирующую учёт контингента обучающихся, учебных групп, курсов, контроль посещаемости, разграничение доступа по ролям и формирование отчётности для образовательной организации УИС.

**Задачи?**
Проанализировать предметную область и нормативную базу, спроектировать архитектуру и модель данных, разработать ролевую модель, реализовать учёт студентов/групп, электронный табель, автоперевод курса, импорт из Excel и отчётность, протестировать результат.

**Объект и предмет исследования?**
Объект — процессы учёта контингента и посещаемости в образовательной организации УИС. Предмет — методы и программные средства их автоматизации: модель данных, ролевой доступ, отчётность.

**Актуальность?**
Ручной учёт (бумага, разрозненный Excel) не даёт целостности данных, истории изменений и разграничения доступа к персональным данным обучающихся — единая информационная система снимает эти риски.

**Практическая значимость?**
Рабочий прототип, демонстрирующий полный цикл автоматизации ключевого учебного процесса; может быть основой для доработки под конкретное учреждение и методическим примером RBAC-системы со scope-доступом.

## Технические вопросы

**Почему именно такой стек (Angular + NestJS + PostgreSQL + Prisma)?**
Angular и NestJS дают строгую типизацию и DI «из коробки» на обеих сторонах — меньше ошибок в контракте между клиентом и сервером. PostgreSQL — потому что предметная область реляционна по своей природе (студент → группа → направление, табель → период → причина), а не документо-ориентирована. Prisma — типобезопасные запросы, генерируемые из схемы: опечатка в имени поля — ошибка компиляции, а не рантайм-баг в проде. Подробное обоснование каждого выбора — `docs/02-architecture-and-stack.md`.

**Почему модульный монолит, а не микросервисы?**
Одна зона ответственности, один backend-процесс, нет необходимости в независимом масштабировании частей системы. Микросервисы решают проблемы координации больших распределённых команд и независимого деплоя — здесь этих проблем нет, а цена (сетевые вызовы вместо вызовов функций, распределённые транзакции) была бы чистыми издержками. При этом внутри монолита модули изолированы на уровне кода — NestJS-модули с явными границами через `imports`/`exports`.

**Почему frontend и backend — разные приложения, а не одно?**
Чтобы бизнес-логика физически не могла «утечь» в браузер: у frontend нет доступа к исходникам backend (разные `node_modules`, разные `tsconfig`), связь только через HTTP. Это также разделяет жизненные циклы деплоя — можно обновить один без другого.

**Почему без Docker?**
Контейнеризация — операционная надстройка, а не часть бизнес-логики. Для первой рабочей версии важнее, чтобы запуск был максимально прозрачным и объяснимым (`npm install` → `npm run start:dev`), чем добавлять ещё один слой инфраструктуры поверх уже нетривиальной системы из двух процессов и БД. Это осознанно указано как направление развития, не забытая деталь.

**Как работает RBAC?**
Два уровня: permission (что можно делать — например, `ATTENDANCE_WRITE`) и scope (на каких объектах — конкретные группы или направления пользователя). Guard на backend проверяет permission декларативно через декоратор `@Roles()`, а сервис дополнительно фильтрует выборку данных по scope прямо в SQL-запросе. Проверка всегда на сервере — интерфейс может скрыть кнопку, но это не единственная линия защиты.

**Как работает табель?**
При создании табеля все активные студенты группы автоматически отмечаются присутствующими. Старшина отмечает отсутствующих (по одному или массово через чекбоксы), обязательно указывая причину — без причины система отклонит запрос на уровне API, не только формы. Отправить табель на проверку нельзя, пока не у каждого студента указана явка и не у каждого отсутствующего — причина.

**Как работает импорт Excel?**
Четыре шага: разбор файла (сервер сохраняет ВСЕ строки, не только превью из 10), сопоставление колонок, валидация каждой строки (существование группы/программы/статуса), подтверждение — реальное создание студентов в одной транзакции. Число импортированных строк всегда точно равно числу прошедших валидацию.

**Как работает автоматический перевод курса?**
Предпросмотр показывает, кто перейдёт на следующий курс (если курс меньше `maxCourse` программы) и кто завершит обучение (если достиг максимума) — без изменения данных. Выполнение применяет переходы транзакционно и идемпотентно: повторный запуск в том же учебном году не переводит уже переведённых студентов повторно — это проверяется по наличию соответствующей записи в истории курса с начала текущего учебного года.

**Как обеспечивается безопасность?**
Пароли — только Argon2-хеш. JWT с коротким временем жизни access-токена. RBAC + scope на каждом защищённом эндпоинте. `class-validator` на всех входных DTO (`whitelist + forbidNonWhitelisted` — лишние поля в запросе отклоняются, а не тихо игнорируются). `helmet` для HTTP-заголовков, ограниченный CORS. Секреты — в `.env`, не в репозитории.

## Сложные вопросы (готовые ответы)

**Почему CRM, а не просто Excel?**
Excel не даёт целостности данных (ничто не мешает ввести несуществующую группу), не разграничивает доступ к персональным данным, не хранит историю изменений и требует ручного пересчёта отчётности при каждом изменении. Информационная система переносит эти гарантии на уровень СУБД и кода, а не полагается на дисциплину пользователя.

**Почему не MongoDB?**
Данные предметной области — реляционные по своей природе: студент принадлежит группе, группа — направлению и программе, табель ссылается на период, группу и причины отсутствия. Document-store не даёт ничего взамен потерянной ссылочной целостности (внешних ключей, каскадов, уникальных ограничений на уровне БД), а эти гарантии здесь критичны — например, уникальность табеля на комбинацию «группа+период+дата» реализована именно ограничением БД, а не только проверкой в коде.

**Насколько система соответствует реальным требованиям ФСИН?**
Система учитывает открытые нормативные требования, применимые к любой организации, работающей с персональными данными (152-ФЗ) и образовательной деятельностью в целом (273-ФЗ), — минимизация состава хранимых персональных данных, разграничение доступа. Специфические ведомственные приказы ФСИН, регламентирующие именно структуру электронного табеля или карточки обучающегося, в открытом доступе не обнаружены и не использовались как источник требований — соответствующие решения (например, два периода посещаемости в сутки) спроектированы самостоятельно и явно помечены в `docs/09-vkr-materials.md` как проектные, а не нормативные.

**Почему система не готова к промышленному внедрению?**
Это дипломный прототип: нет нагрузочного тестирования, нет аттестации по требованиям защиты информации для реальной ГИС, нет резервного копирования и мониторинга, ограниченный набор автоматических тестов (18 тестов — покрывают ключевые бизнес-правила, но не весь функционал), не проводился security-аудит. Для промышленной эксплуатации потребовалась бы отдельная работа по этим направлениям.

**Что можно улучшить / дальнейшее развитие?**
Docker-контейнеризация для упрощения развёртывания, страница профиля/личного кабинета пользователя, frontend-страница отчёта по конкретному студенту (backend уже готов), уведомления (email), расширение тестового покрытия на frontend, интеграция с внешними системами учёта, при необходимости — переход на микросервисную архитектуру, если появится реальная потребность в независимом масштабировании отдельных частей.

**Как проверялась работоспособность системы?**
Помимо 18 автоматических unit- и e2e-тестов на изолированной тестовой базе данных, все ключевые сценарии прогонялись вручную через настоящий браузер (Playwright) поверх реального backend и реальной PostgreSQL — не моки. Это позволило найти и исправить реальные дефекты уже после того, как код «выглядел» рабочим (см. таблицу дефектов в `docs/06-testing.md`), включая ошибку идемпотентности автоперевода курса и уязвимость с клиентоуправляемым `organizationId`.

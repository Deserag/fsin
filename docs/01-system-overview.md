# Как работает система

## Назначение

Информационная система учёта контингента обучающихся и контроля посещаемости образовательной организации уголовно-исполнительной системы. Автоматизирует то, что в институте иначе ведётся вручную или в разрозненных таблицах: карточки студентов, состав учебных групп, ежедневный табель посещаемости, автоматический перевод студентов на следующий курс, импорт списков из Excel и базовую отчётность.

Документ описывает **фактически реализованную** версию системы по состоянию на дату написания — не план, не намерение, а то, что реально работает и проверено через реальный backend, реальную PostgreSQL и реальный браузер.

## Кто пользуется системой

Три роли, разграниченные по правам и по видимым данным (RBAC + scope):

| Роль | Кто это | Что видит |
|---|---|---|
| Администратор | Сотрудник учебного отдела | Всё: все группы, все студенты, все пользователи, все настройки |
| Руководитель / куратор | Начальник направления | Группы и студентов своих направлений (по `directionScope`) |
| Старшина | Назначенный студент/сотрудник группы | Только свою группу (или несколько, если назначен на них) |

Аккаунты студентов в системе не создаются — старшина ведёт табель как назначенный пользователь, а не как обучающийся.

## Основные разделы

- **Главная (dashboard)** — сводка, разная для каждой роли (у админа — счётчики + табели за сегодня, у старшины — свои группы, у руководителя — незаполненные табели по направлению)
- **Табель** — заполнение посещаемости: выбор группы/периода/даты, массовая отметка присутствия/отсутствия, причины, отправка на проверку
- **Студенты** — список с поиском, карточка, создание/редактирование (для админа и руководителя)
- **Группы** — список, создание, назначение старшины, архивирование
- **Отчёты** — сводный отчёт по всем группам и подробный отчёт по одной группе, экспорт в Excel
- **Администрирование** (только админ):
  - Пользователи — создание, роли, доступы (scope), блокировка
  - Роли и права — матрица permission × роль
  - Справочники — направления, программы, учебные годы, статусы студентов, периоды посещаемости, причины отсутствия, поля табеля
  - Импорт Excel — мастер загрузки списка студентов
  - Перевод курса — предпросмотр и выполнение автоматического перевода
  - Организация — реквизиты организации
  - Журнал аудита — кто, что и когда изменил

## Главный пользовательский сценарий

Табель — центральный процесс системы:

```
Старшина логинится
  → открывает «Табель»
  → выбирает группу (обычно одна — своя), период (Утро/Вечер), дату
  → система создаёт табель, где ВСЕ студенты по умолчанию отмечены присутствующими
  → старшина выделяет отсутствующих (чекбоксы + «выбрать всех» + поиск)
  → массово отмечает их отсутствующими и указывает причину
  → система не даёт отправить табель, пока не у каждого студента указана явка,
    а у каждого отсутствующего — причина
  → «Отправить на проверку» → статус меняется на SUBMITTED
```

Дальше руководитель/админ может «проверить» (REVIEWED) и админ — «закрыть» (CLOSED) табель; закрытый табель никто не может редактировать.

## Как взаимодействуют части системы

```
Angular (frontend, :4200)  --HTTP/JSON-->  NestJS (backend, :3000/api)  --Prisma-->  PostgreSQL
```

Frontend — полностью отдельное приложение, не знает о существовании Prisma или структуры БД. Backend — единственный владелец бизнес-логики и данных; никаких прямых обращений к базе из браузера. Авторизация — JWT (access-token в заголовке `Authorization: Bearer`), хранится в `localStorage` на клиенте.

## Где что хранится

Вся persistenная информация — в PostgreSQL, единая база на организацию (модель `Organization` заложена как контейнер, чтобы систему можно было развернуть для другого учреждения без переписывания кода). Загруженные Excel-файлы не сохраняются на диск — обрабатываются в памяти, а промежуточные данные импорта (строки, сопоставление колонок, ошибки) хранятся в таблице `import_jobs`.

## Функция → куда смотреть

Для каждой функции: кто её использует, где реализована логика, какие таблицы БД задействованы.

### Заполнение табеля
- **Пользователь:** старшина (и руководитель/админ — по своим группам)
- **Frontend:** `frontend/src/app/features/attendance/`
- **Backend:** `backend/src/attendance/` (`AttendanceService`, `AttendanceController`)
- **БД:** `AttendanceSheet`, `AttendanceRecord`, `AttendanceReason`, `AttendancePeriod`
- **Логика:** при создании табеля все активные студенты группы автоматически получают запись `isPresent: true`; смена на `false` требует `reasonId`; отправка на проверку (`submit`) проверяет, что `present + absent === totalCount` и что у всех отсутствующих указана причина

### Управление студентами и группами
- **Пользователь:** админ, руководитель
- **Frontend:** `frontend/src/app/features/students/`, `frontend/src/app/features/groups/`
- **Backend:** `backend/src/students/`, `backend/src/groups/`
- **БД:** `Student`, `Group`, `StudentGroupHistory`, `StudentStatusHistory`, `GroupForeman`
- **Логика:** перевод студента в другую группу / смена статуса всегда пишет запись в соответствующую историю; исторические записи посещаемости не меняются при смене текущего состояния студента (внешний ключ, а не денормализованная копия)

### Автоматический перевод курса
- **Пользователь:** админ
- **Frontend:** `frontend/src/app/features/admin/course-transition/`
- **Backend:** `backend/src/students/course-transition.service.ts`
- **БД:** `Student`, `StudentCourseHistory`, `StudentStatus`, `AcademicYear`, `AuditLog`
- **Логика:** `preview()` — только чтение, показывает кто на какой курс перейдёт и кто завершит обучение (курс ≥ `program.maxCourse`); `execute()` — транзакционно применяет изменения, идемпотентно в рамках одного учебного года (студент с уже существующей автоматической записью в `StudentCourseHistory` с начала текущего `AcademicYear` повторно не переводится)

### Импорт студентов из Excel
- **Пользователь:** админ
- **Frontend:** `frontend/src/app/features/admin/imports/`
- **Backend:** `backend/src/imports/`
- **БД:** `ImportJob`, `ImportError`, `Student`
- **Логика:** 4 шага — parse (весь файл разбирается и сохраняется целиком в `ImportJob.rawData`, клиенту показываются только первые 10 строк) → mapping (сопоставление колонок) → validate (проверка ВСЕХ строк, не только превью) → confirm (реальное создание студентов в транзакции); частичный импорт не выполняется скрыто — итоговое число импортированных строк всегда равно числу прошедших валидацию

### RBAC и scope-доступ
- **Пользователь:** все
- **Backend:** `backend/src/auth/guards/roles.guard.ts`, проверки `groupScopeIds`/`directionScopeIds` внутри каждого сервиса
- **БД:** `Role`, `Permission`, `RolePermission`, `UserRole`, `UserGroupScope`, `UserDirectionScope`
- **Логика:** JWT несёт роли и permissions; guard проверяет наличие permission, а сервисы дополнительно фильтруют выборку по scope (например, `GroupsService.findAll` для старшины подставляет `id: { in: userContext.groupScopeIds }`)

### Отчётность и экспорт
- **Пользователь:** админ, руководитель
- **Frontend:** `frontend/src/app/features/admin/reports/`
- **Backend:** `backend/src/reports/`, `backend/src/exports/`
- **БД:** агрегация по `AttendanceSheet`/`AttendanceRecord`
- **Логика:** сводный отчёт считает посещаемость по каждой активной группе за период; отчёт по группе добавляет разбивку по причинам отсутствия; экспорт формирует `.xlsx` через `exceljs` и отдаёт файл потоком, без сохранения на диск

### Журнал аудита
- **Пользователь:** админ
- **Frontend:** `frontend/src/app/features/admin/audit/`
- **Backend:** `backend/src/audit/`
- **БД:** `AuditLog`
- **Логика:** запись создаётся при значимых операциях (создание/изменение студента, группы, пользователя, действия с табелем, назначение старшины, импорт, автоперевод курса) с указанием пользователя, действия, сущности и — где применимо — старого/нового значения

## Ограничения текущей версии

- Учебные годы, направления, программы, статусы и т.п. создаются вручную через админ-панель — нет отдельного мастера первоначальной настройки организации
- Уведомления (email/push) не реализованы — обратная связь только внутри интерфейса (тосты) и через журнал аудита
- Отчёт по студенту (`GET /reports/student/:id`) реализован на backend, но не имеет отдельной frontend-страницы — доступен только через API
